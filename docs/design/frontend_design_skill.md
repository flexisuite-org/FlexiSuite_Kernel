# FlexiSuite Lumina Frontend Design & UX Guidelines

FlexiSuite のフロントエンドを設計・実装する AI エージェント／人間開発者のための  
**「世界観・UX・実装」を一貫させるためのガイドライン**。

このドキュメントは、`apps/launcher` を中心とした FlexiSuite の Web UI 全体に適用する。
「とにかく使いやすく」「無駄じゃない」「でも美しい」ライトテーマを作ることが目的。

---

## 1. Purpose & Context First

まず「何を、誰のために作るのか」を毎回はっきりさせる。

- **目的**  
  - 日々の業務で FlexiSuite を使う人が、迷わず・速く・安心してタスクをこなせること。
  - Launcher は「アカウント・グループ・アプリ」をつなぐハブであり、迷わない動線が最優先。
- **利用者**  
  - 情報ワーカー / チームリーダー / 管理者が中心。  
  - PC 大画面メイン、将来モバイル対応も視野に入れる。
- **ユースケース**  
  - ログイン → 所属グループの確認 → アプリ起動  
  - 招待からのサインアップ → グループ参加  
  - 設定・アカウント管理・グループ管理
- **制約**  
  - Next.js App Router + Tailwind CSS。  
  - ライトテーマのみ。アクセシビリティ (WCAG AA 相当) を必須要件とする。

> UI は目的の奴隷であり、美しさは「目的を邪魔しない形」でのみ許される。

---

## 2. Aesthetic Direction: Lumina Light

FlexiSuite の世界観は **「透き通ったライトテーマ × Raspberry Pink (#c2255d)」** で統一する。

- キーワード:  
  **Clarity / Freshness / Human Warmth / Functional Minimalism**
- 方向性:
  - ライトテーマのみ。背景は白〜ごく薄いグレーを基調とする。
  - アクセントカラーは基本的に `#c2255d` のみをメインとし、他のビビッドカラーは極力使わない。
  - 角丸・影・ボーダーは「構造とヒエラルキーを説明するため」にだけ使う。
  - 派手な装飾やガラスモーフィズムは **原則禁止**。必要なときも「1画面に1箇所まで」。

> 「中途半端な中庸」ではなく、**Lumina Light というひとつの世界観**に全てを揃える。

---

## 3. Typography: Inter + Japanese

FlexiSuite では、一般的なルールではなく **プロダクトとして Inter を正式採用**する。
ただし日本語表示を想定し、フォールバックを含めてきちんと設計する。

- **ベースフォント**
  - Latin: `Inter`
  - Japanese: `Noto Sans JP` など、素直で読みやすいサンセリフ
- 推奨スタック例（Tailwind / next/font 側で設定）:
  - `font-sans: ["Inter", "Noto Sans JP", system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif]`
- 用途:
  - 見出し: Inter / Noto Sans JP の太め (`font-semibold`〜`font-bold`)、`tracking-tight`。  
  - 本文: 標準ウェイト (`font-normal`〜`font-medium`)、`leading-relaxed`。  
  - ラベル・メタ情報: `text-sm`、`font-medium`。
- NG:
  - コンポーネントごとに別フォントを混在させる。  
  - 不必要に Display フォントを足して世界観を壊す。

> 世界観の 6 割はフォントで決まる。FlexiSuite では「Inter + 日本語 Sans」を迷わず使う。

## 4. Color & Theme: #c2255d を中心にした物語

ライトテーマの中で **Raspberry Pink (#c2255d)** を唯一の強い主役として扱う。

- **Primary Accent**
  - `#c2255d` を `--color-primary` として定義し、ボタン・リンク・アクティブ状態・主要ハイライトに使用。
  - 使い過ぎない。1画面で「ここが一番大事」というポイントに集中させる。

- **Neutrals / Background**
  - Base: `#ffffff` (`bg-white`)
  - Surface Alt: `#f8f9fa` (`bg-slate-50` or `bg-surface-alt`)
  - Body Background: ごく薄いグラデーションやノイズを使う場合も、`#c2255d` をほんの少し混ぜる程度に止める。

- **Text**
  - Primary: `#1e293b` (`text-slate-800`)
  - Secondary: `#64748b` (`text-slate-500`)
  - プレースホルダや補足情報は `text-slate-400` 前後。

- **Semantic Colors**
  - Success / Warning / Error は Tailwind の標準トーンをベースにしつつ、彩度をやや抑える。
  - Error 表示は背景を淡色 (`red-50` など) にし、文字は `red-600` 程度で読みやすさ優先。

> 色は「画面内でどこを見るべきか」を指示するためだけに使う。カラフルさを競わない。

## 5. Layout, IA & Navigation

UI/UX の最優先は「迷わないこと」「同じ目的はいつも同じ場所にあること」。

- **情報構造の基本原則**
  - 「アカウント全体」「グループ」「アプリ」のレイヤーを混在させない。
    - アカウント設定: ユーザー個人に紐づくもの。
    - グループ: 所属やロール、インストールされたアプリ。
    - アプリ: 実際の業務機能。
  - ナビゲーション階層は可能な限り浅く保ち、2階層を基本とする。

- **Launcher / Dashboard の構図**
  - 左: ナビゲーション（グローバル / グループ切り替え）。  
  - 右: 選択済みコンテキスト（現在のグループ / アプリ一覧 / 招待 / 設定など）。
  - ページタイトル・説明文・主要アクションを、常にファーストビューの左上〜中央にまとめる。

- **動線設計の原則**
  - ログイン後の初期着地は常に「ユーザーにとって一番意味のある場所」（通常は現在のグループの Launcher）。
  - 招待経由のサインアップは、成功後に自動的に該当グループにフォーカスして状態を見せる。
  - 設定画面は「迷子になりがちな場所」なので、戻り先（Launcher / Dashboard）を常に明示する。

> 新しい画面や機能を追加するときは、「ユーザーがここに来る前の状態」と「ここからどこに行くか」を必ず図にしてから UI を決める。

## 6. Motion: 無駄のない、静かなモーション

アニメーションは **「気持ちよさ」ではなく「理解を助けるため」にだけ使う**。

- 基本方針
  - デュレーションは 150–250ms を基準にし、速すぎず・遅すぎず。
  - `ease-out` / `ease-in-out` ベースで、「ふわっと入ってサッと消える」感覚。
  - 1画面あたり「大きなモーション」は 1〜2 箇所まで。

- 具体例
  - ロード中: スケルトン / シマーよりも、シンプルなスピナー + 最小限のフェードで済ませる。
  - ページトランジション: コンテンツの `fade-in` + `slide-up` 程度。大きなパララックスは避ける。
  - グループ切り替え / アプリグリッド更新: 古い内容をフェードアウトし、新しい内容をフェードインさせる。  

- NG
  - 目的に関係しない常時アニメーション（無限ループの装飾など）。
  - 注意を奪う激しいモーション。

> 「動いているからかっこいい」は禁止。動くなら必ず理由を書く。

## 7. Accessibility & Inclusivity

アクセシビリティは「後付けで頑張るもの」ではなく、最初から UI 設計の一部とする。

- **コントラスト**
  - テキストと背景のコントラストは、原則 WCAG AA を満たす。  
  - 薄いテキストや Disabled 表現は、意味が伝わる前提でのみ使用する。

- **フォーカス & キーボード操作**
  - すべてのインタラクティブ要素は Tab で巡回できるようにする。
  - カスタムコンポーネントでも `button` / `a` など適切なセマンティック要素を使い、`role` で代用しないことを基本とする。
  - フォーカスリングは消さず、Tailwind の `ring` を使って Lumina らしい見た目に整える。

- **ARIA & セマンティクス**
  - ナビゲーションには `nav`、メインコンテンツには `main` を使う。
  - アイコンのみのボタンには `aria-label` を必ず付ける。

- **多言語・日本語**
  - 日本語と英語が混在することを前提に、文字幅・改行・行間に余裕を持たせる。
  - 固有名詞以外はどちらの言語でも意味が通るラベル文言を心がける。

---

## 8. Component & Code Principles

実装は常に「プロダクション品質」「機能美」を満たすこと。

- **コンポーネント設計**
  - 再利用したい「パターン」は `components/ui` / `components/launcher` などに切り出す。
  - 1コンポーネントの責務を絞り、ロジックと見た目を過度に混在させない。

- **Tailwind / テーマ**
  - 色やスペーシングは極力トークン（クラス / CSS variables）を通して指定する。
  - ad-hoc な `text-[#xxxxxx]` や `bg-[#xxxxxx]` を増やさない。

- **アクセシビリティ・UX を壊さないリファクタ**
  - デザインを変えるときは、フォームのバリデーションメッセージ / フォーカス時の挙動 / スクリーンリーダーの読み上げ順も確認する。

## 9. Design & Implementation Workflow

新しい画面や大きな改修を行うときは、次のステップを守る。

1. **目的とユーザーストーリーを言語化する**  
   - この画面でユーザーは何を達成したいのか？  
   - Before / After の状態は何か？
2. **情報構造と動線を描く**  
   - どのナビゲーションから来るか、どこへ遷移できるかを簡単な図で整理する。
3. **Lumina Light らしい構図を決める**  
   - どこにタイトル・主要アクション・サブ情報を置くか。  
   - #c2255d をどこに集中させるか。
4. **タイポ・カラー・コンポーネントを決める**  
   - このドキュメントと `design_system.md` に沿って選ぶ。
5. **モーションと状態変化を設計する**  
   - ローディング・エラー・空状態・成功状態を定義する。
6. **実装 → 手で触りながら微調整**  
   - キーボードで操作し、スクリーンを狭めたり広げたりしながら、使いやすさを確認する。

## 10. このドキュメントの位置づけ

- この `frontend_design_skill.md` は「FlexiSuite Lumina 全体のデザイン・UXの考え方」を定義する。
- `design_system.md` は、ここで定義した考え方に沿った **具体的なトークン・コンポーネント仕様** を補完するドキュメントとして扱う。
- 迷ったときは:
  1. まずここ（考え方・世界観）を優先し、  
  2. 次に `design_system.md` を参照して具体値を決める。

> 結論: FlexiSuite のフロントエンドは、  
> 「ライトテーマ × #c2255d × Inter + 日本語 Sans」な世界観の中で、  
> とにかく使いやすく、無駄がなく、しかし静かに美しい UI を目指す。
